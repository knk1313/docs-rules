# schemas/

文書種別ごとの必須セクションと文書構造を置く。1種別1ファイルで、ファイル名はSKILL.mdの識別名に合わせる（例：`session-log.md`）。表記・文体のルールはここに書かず、[rules/](../rules/README.md)を参照する。

## ファイルの分け方

文書種別ごとのファイルと識別名は次のとおり。

| ファイル | 種別 | 識別名 |
| --- | --- | --- |
| [session-log.md](session-log.md) | セッションログ | `session-log` |
| [proposal.md](proposal.md) | 提案書 | `proposal` |

## 1種別の書き方

各種別のファイルは、次の`##`見出しをこの順に置く。見出し名は変えない。

1. `## 目的と読み手`：何のための文書か、誰が読むか
2. `## 入力`：何を材料に書くか。ほかの種別を入力にできる場合は、その対応表を置く
3. `## 必須セクション`：必須セクションの表（書式は次の節）
4. `## セクションごとの書き方`：必須セクションごとに、書くこと・書かないこと・粒度の目安
5. `## 文書全体の制約`：見出しの使い方や文体など、文書全体に掛かる制約

## 必須セクション表の書式

必須セクションは、次の書式の表で示す。この表を見出し名の唯一の定義場所とする。`templates/`の見出しは、この表の見出し名をそのまま使う。

```markdown
| 順 | 見出し名 | 役割 |
| --- | --- | --- |
| 1 | `## 概要` | 一言で役割を書く |
```

- 列は「順」「見出し名」「役割」の三つに固定する
- 「見出し名」は、文書に書く見出しの文字列を、先頭の`##`と半角スペースも含めてバッククォートで囲む
- 書式を固定しておき、`evaluators/`を実装するとき（Step 2）に見出し名と順序を正規表現で拾えるようにする

## セクションごとの書き方の書式

`## セクションごとの書き方`の下には、必須セクションごとに`###`の見出しを表の順に置き、次の3項目を書く。見出しは表の見出し名から先頭の`##`と半角スペースを除いたものにする。

```markdown
### 概要

- 書くこと：そのセクションに書く内容
- 書かないこと：別のセクションに回す内容と、この文書に書かない内容
- 粒度の目安：文量と具体性の目安
```

- 粒度の目安のうち、文量は「3文以内」「1項目1〜2文」のように数で書く。具体性は「日付と数値を入れる」のように観点で書く
- 粒度の目安は目安であり、守れているかはAIが判定する。機械では判定しない

## 見出しの規約

全種別に共通する見出しの使い方を示す。種別のファイルで上書きする場合は、その種別の`## 文書全体の制約`に書く。

- `#`は文書名に一つだけ使う
- `##`は、必須セクションを表の順にすべて置く。書く内容がないセクションも省かず、その旨を一文で書く
- 任意の`##`見出しは、最後の必須セクションより後ろにだけ足せる。必須セクションの間には挟まない
- `###`以下は、各セクションの中で自由に使える

## 判定の範囲

evaluators/（Step 2）で機械判定するのは次の2点だけとする。

- 必須セクションの見出しがすべてあるか
- 必須セクションの見出しが表の順に並んでいるか（間に別の見出しがあるかどうかではなく、必須セクション同士の相対順序を見る）

セクションの中身と粒度の目安はAIが判定する（[prompts/evaluate.md](../prompts/evaluate.md)）。

## 文書種別の決め方

種別ごとの構成は、読み手がその文書を開く目的から決める。目的を整理する枠組みにはDiátaxisの4分類を使い、構成の細部はGoogle Developer Documentation Style Guide（以下、Googleのガイド）の観点で決める。どちらも原文は写さず、考え方を書き直している。

### Diátaxisの二つの軸と4分類

Diátaxisは、読み手の必要を二つの軸で分ける。

| 軸 | 一方の極 | もう一方の極 |
| --- | --- | --- |
| 何をするための文書か | 行動（action）：読みながら手を動かす | 理解（cognition）：読んで知る、考える |
| どの場面で読むか | 学習（acquisition）：身に付けるために読む | 仕事（application）：作業の最中に読む |

二つの軸を組み合わせると、次の4分類になる。

| 分類 | 軸の組み合わせ | 読み手の問い | 構成の特徴 |
| --- | --- | --- | --- |
| チュートリアル | 行動×学習 | 教えてほしい | 一つの道筋をたどらせ、手を動かしながら身に付けさせる |
| ハウツー | 行動×仕事 | どうすればよいか | 目的を果たすための手順を順に並べる |
| リファレンス | 理解×仕事 | 何がどうなっているか | 事実を、引きやすい決まった型で並べる |
| 解説 | 理解×学習 | なぜそうなのか | 背景や理由を示し、全体の見通しを与える |

- 一つの文書は、読み手の一つの目的に応える。複数の分類を一つの文書に混ぜると、どの目的にも応えにくくなる
- 隣り合う分類（チュートリアルとハウツーなど）は混ざりやすい。種別を決めるときは、どちらの目的を主にするかを先に決める

### Googleのガイドから取る観点

構成の細部は、Googleのガイドの次の観点で決める。英語の文体のルール（大文字の使い方、句読点など）は取り込まない。

| 観点 | 内容 | `schemas/`での扱い |
| --- | --- | --- |
| 冒頭で範囲を示す | 文書が扱う範囲、前提とする知識、扱わない範囲を冒頭で示す | 各種別の`## 目的と読み手`に、読み手の前提と対象外を書く |
| 見出しの下に本文を置く | 見出しの階層を飛ばさず、見出しの下には必ず本文を置く | 「見出しの規約」の、書く内容がないセクションもその旨を一文で書く、に当たる |
| 箇条書の種類を使い分ける | 順序に意味がある項目は番号付き、順序のない項目は番号なしで並べる | 決定事項や手順のように順に読む項目は、番号付きの箇条書を求める |
| 手順は一つの手順に一つの動作 | 手順の前に目的や必要なものを示し、一つの手順には一つの動作だけを書く | 次の作業や決定後の手順を書くセクションの「書くこと」に反映する |

### 既存の種別の位置づけ

既存の種別が4分類のどれに近いかは次のとおり。

| 種別 | 主な読み手の目的 | 近い分類 | 分類に収まらない部分 |
| --- | --- | --- | --- |
| セッションログ | 仕事の最中に、決まったことと次の作業を引く | リファレンス（決めたこと、参照）、解説（決めた理由、検討した経緯） | 記録の文書の例外として、一つの文書に複数の目的が混ざる。次に引き継ぐことはハウツーに近い |
| 提案書 | 先方が意思決定する | 解説（背景と課題、推奨案と理由） | 分類の外。決定を求める構成（決めてほしいこと、選択肢と比較、決定後に起きること）は、提案書のスキーマで独自に定める |

- 記録の文書の例外：セッションログは、起きたことを1か所に残すことが目的のため、分類ごとに文書を分けない。分類ごとの見出しで目的の切れ目を示す
- 分類の外：意思決定を求める文書のように、4分類のどれにも当たらない種別は、表に「分類の外」と書き、構成を種別のスキーマで定める

### 種別を足すときの判断の順

1. 読み手がその文書を開く目的を一つに決める
2. 4分類から近い分類を選ぶ。どれにも当たらないときは「分類の外」とする
3. 近い分類に収まらない部分を、種別のスキーマで独自に定める
4. 上の「既存の種別の位置づけ」の表に1行足す

## 種別を足す手順

1. 「文書種別の決め方」の判断の順に従って種別の位置づけを決め、「既存の種別の位置づけ」の表に1行足す
2. SKILL.mdの種別の表に、種別名・識別名・例を足す
3. このディレクトリに`<識別名>.md`を、「1種別の書き方」の型で作る。`## 目的と読み手`には、1で決めた位置づけを「位置づけ」の項目に書く
4. 上の「ファイルの分け方」の表に1行足す
5. `templates/<識別名>.md`を、必須セクション表の見出し名で作る
