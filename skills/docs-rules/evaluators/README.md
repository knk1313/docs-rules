# evaluators/

`rules/`の`判定：機械`のルールをコードで判定するための設定とデータと、書き直しの前後の採点結果を比べるスクリプトを置く。

| 置くもの | 内容 | 状態 |
| --- | --- | --- |
| [score.mjs](score.mjs) | 採点の入口。1コマンドで文書を渡し、違反の一覧をJSONで返す | 置いた（#21） |
| [compare.mjs](compare.mjs) | 書き直しの前後の採点結果を比べ、直った違反、残った違反、新しく出た違反、2回続けて残った違反を返す | 置いた（#24） |
| [package.json](package.json) | 採点で使うパッケージと版 | 置いた（#21） |
| [package-lock.json](package-lock.json) | 依存の依存まで含めた版の一覧。`score.mjs`はこの版のとおりにパッケージを入れる。Dependabotが既知の脆弱性の検出と版上げに使う | 置いた |
| [textlintrc.json](textlintrc.json) | textlintの設定 | 置いた（#21） |
| [prh/](prh/) | textlint-rule-prhの辞書 | 置いた（#21） |
| [custom-rules/](custom-rules/) | 自前のtextlintルール。`lib/`はその共通部分 | 置いた（#21） |
| [allowed-terms.json](allowed-terms.json) | 採点で指摘しない語（ルールIDごと）。`--rulesdir`のルールには`textlintrc.json`の設定値が渡らないため、ルールがこのファイルを直接読む | 置いた |
| [data/](data/README.md) | 内閣告示の判定データ（JSON） | 置いた（#11） |
| [docs-rules.markdownlint-cli2.jsonc](docs-rules.markdownlint-cli2.jsonc) | markdownlintの設定 | 置いた（#14） |

設定ファイルの名前は「.」で始めない。スキルをzipでアップロードする経路などで「.」で始まるファイルが落ち、採点が設定なしで動かなくなるため。`score.mjs`は`--config`で設定ファイルのパスを渡す。markdownlint-cli2は名前の末尾が`.markdownlint-cli2.jsonc`のファイルを自分の設定として読むため、`docs-rules.`を前に付けた。

## 採点の入口

### 使い方

```bash
node skills/docs-rules/evaluators/score.mjs <文書のパス> [--type <識別名>]
```

- 前提：Node.js 18以上とnpm。`score.mjs`は標準モジュールだけで書いてあり、利用者に事前の`npm install`を求めない（#13の決定）
- `--type`：文書種別の識別名（`session-log`、`proposal`など）を渡すと、`schemas/<識別名>.md`の必須セクション表と文書の`##`見出しを順序込みで突き合わせる。テンプレートの案内のコメント（`<!--`で始まる部分）が残っていないかも見る。渡さないときはこの照合を飛ばす。`--type=<識別名>`の形でも渡せる
- 案内のコメントの照合では、コードブロックの中の`<!--`を対象にしない。囲み型と、空行の後を4字以上字下げした型の両方である
- 直前がバッククォート、かぎ括弧、二重かぎ括弧、引用符の`<!--`も対象にしない。記法の説明に書いたものを消し忘れと誤って指摘しないため

### パッケージの入れ方

textlintとmarkdownlint-cli2は、初回の実行で`score.mjs`が自分で入れる。

- 版：[package-lock.json](package-lock.json)のとおりに`npm ci`で入れる。依存の依存まで版が決まっているため、利用者の手元とCIで同じ版が動く。版を上げるときは、この文書の表と`rules/`の`判定`欄を見直す
- インストール時のスクリプトは動かさない（`--ignore-scripts`）。依存の中にスクリプトが要るパッケージはない
- 入れる場所：利用者のキャッシュ。環境変数`DOCS_RULES_CACHE_DIR`で変えられる。プラグインの`${CLAUDE_PLUGIN_DATA}`は、エージェントが実行するコマンドの環境変数に渡らないため使わない
  - macOS：`~/Library/Caches/docs-rules`
  - Linux：`~/.cache/docs-rules`。`XDG_CACHE_HOME`があればその下
  - Windows：`%LOCALAPPDATA%\docs-rules`
- 入れ直す条件：場所の名前にロックファイルのハッシュを含める。ロックファイルが変わると別の場所に入れる
- 前の版の場所：使うたびに場所の更新日時を今にする。新しく入れたときに、別の版の場所のうち7日より長く使っていないものを消す。別の版のスキルが並行して動いていても、使用中の場所は消さない
- 並行して呼ばれたとき：一時的な場所に入れ終えてから名前を変えるため、入れかけの場所は使われない
- 起動：入れたパッケージのコマンドをNode.jsで直接起動する。シェルを通さないため、文書のパスに「&」などが含まれていてもコマンドとして動かない
- 初回の実行は、パッケージの取得に数秒から20秒ほどかかる。2回目からは入れたものを使う

### 終了コード

終了コードごとの意味と、利用者への扱いは次のとおり。

| 終了コード | 意味 | 利用者への扱い |
| --- | --- | --- |
| 0 | 違反なし | そのまま出力してよい |
| 1 | 違反あり | `violations`を見て直す |
| 2 | 引数の誤り（文書がない、文書のパスがファイルでない、文書を読めない、`--type`に値がない、`schemas/`にない識別名、知らないオプション、文書のパスが二つ以上） | 引数を直して実行し直す |
| 3 | textlintかmarkdownlint-cli2を実行できなかった（ネットワークがなくパッケージを入れられない、npmがないなど） | 機械判定を飛ばし、そのことを利用者に伝えたうえで、SKILL.mdの自己点検に戻る |

Node.jsがない環境では`node`のコマンドが見つからない。この場合も終了コード3と同じく扱う。

### 採点結果の形式

標準出力にJSONを一つ返す。項目名は、AI評価（#23）の結果と同じにする。

```json
{
  "file": "session-log.md",
  "checked_rules": ["FW-001", "NOT-016", "SCHEMA"],
  "skipped_rules": [{ "rule_id": "NOT-006", "reason": "一部は機械で判定しない：表にない音訓は、語の読みを決める形態素解析が要るため、AI評価で扱う。" }],
  "violations": [
    {
      "rule_id": "NOT-016",
      "line": 12,
      "column": 2,
      "excerpt": "ヶ",
      "fix": "「ヶ」→「か」",
      "judge": "機械",
      "checker": "textlint：jtf-style/2.2.3.一部の助数詞の表記"
    }
  ]
}
```

| 項目 | 意味 |
| --- | --- |
| `checked_rules` | 採点したルールID。`rules/`の`判定：機械`のうち、`判定`欄に判定手段が書いてあるもの。`--type`を渡したときは`SCHEMA`を足す。ここにあって`violations`に出ないルールは合格である |
| `skipped_rules` | 採点しなかったルールと理由。一部だけ機械で判定するルールは、`checked_rules`に入れたうえで、ここにも出す。理由は、`rules/`の注記のうち「AI評価で扱う」と書いた文である。この部分は、`violations`に出なくても合格とは限らない |
| `violations[].rule_id` | docs-rulesのルールID。必須セクションの照合と、残った案内のコメントは`SCHEMA`。対応するルールがない判定手段（`max-ten`など、docs-rulesにないルール）は`null` |
| `violations[].line` | 該当行（1始まり）。必須セクションの欠落は該当行がないため`null` |
| `violations[].column` | 該当箇所の桁（1始まり）。同じ行に同じ文字列が複数あるときに区別する。必須セクションの欠落は`null`（#22で足した） |
| `violations[].excerpt` | 該当箇所の文字列 |
| `violations[].fix` | 直し方。ツールが修正候補を返したときは`「A」→「B」`の形、返さないときは`rules/`の該当ルールの見出しの要約。対応するルールがないときはツールのメッセージ |
| `violations[].judge` | `機械`。AI評価の結果とまとめるときに区別する |
| `violations[].checker` | 判定手段。`rules/`の`判定`欄と同じ書き方（`textlint：<ルール名>`、`markdownlint：MD0xx`）。必須セクションの照合は`docs-rules/schema` |

- 判定手段とルールIDの対応は、実行のたびに`rules/*.md`の`判定`欄から作る。ルールを足すときに`score.mjs`を直す必要はない
- 一つの判定手段が複数のルールの`判定`欄に書いてあるときは、先に書いてあるルールのIDを返す。ja-no-redundant-expressionはFW-001とFW-002の両方に当たるが、`rule_id`は常にFW-001になる。FW-002の「〜を行う」はprh辞書が`FW-002`で返す
- prh辞書の指摘は、辞書の項目の`prh`に書いたルールIDを返す
- 複数の判定手段が、同じルールIDで同じ箇所（行と桁）を指摘したときは1件にまとめる。直し方の候補（`「A」→「B」`）を返した方を残す。段落の末尾の「．」は、ja-no-mixed-periodとdocs-rules/not-002の両方がNOT-002として指摘する

## 書き直しの前後の比較

SKILL.mdの「4. 点検してから出す」の繰り返しで、書き直した版の採点結果をそれまでの結果と比べる。

```bash
node skills/docs-rules/evaluators/compare.mjs <最初の採点結果> … <前回の採点結果> <今回の採点結果>
```

- `score.mjs`が出力したJSONを、採点した順に二つ以上渡す。`score.mjs`と同じく、Node.jsの標準モジュールだけで書いてある
- 比べるのは`judge`が`機械`の違反だけである。AI評価の`excerpt`は実行ごとに切り出し方が変わり、同じ違反を見分けられないため比べない
- 同じ違反かどうかは、`rule_id`と`excerpt`の組で決める。`rule_id`が`null`のときは`checker`を使う。`line`は書き直しでずれるため使わない
- 同じ組の違反が複数あるときは、件数で比べる。「ヶ」が3か所から1か所に減ったときは、2件が直った違反になる
- 終了コードは、比べられたときが0、引数の誤り（JSONが二つ未満、読めないファイル）のときが2である

出力のJSONの項目は次のとおり。

| 項目 | 意味 |
| --- | --- |
| `files` | 渡した採点結果のパス |
| `rewrites` | 書き直しの回数（渡した採点結果の数から1を引いた数） |
| `fixed` | 前回にあって今回にない違反（前回の採点結果の違反） |
| `remaining` | 前回と今回の両方にある違反（今回の採点結果の違反） |
| `new` | 今回だけにある違反。`SCHEMA`の違反が入っていれば、書き直しで必須セクションの見出しを消したか動かしたか、案内のコメントを足している |
| `stuck` | 直近3回の採点結果すべてにある違反。2回続けて書き直した後も残ったため、以降の書き直しに渡さない |
| `fixed_total` | 最初の採点結果にあって今回にない違反。利用者への報告の「直した違反」に使う |

## textlint

### 方針

- textlintは依存パッケージとして使い、判定条件を写して自前で書くことはしない（#13）。Pythonで自前実装する案は、GRM-004やGRM-005の判定に形態素解析器が要り、利用者の追加インストールが減らないため採らなかった
- 対象は3プリセット（preset-ja-technical-writing、preset-jtf-style、preset-ja-spacing）である。既定で有効なルールを土台にし、docs-rulesの基準と食い違うものと、同じ箇所を重ねて指摘するものだけを無効にする。基準が食い違うときは公用文作成の考え方を優先し、次にJTFスタイルガイドに従う
- プリセットにない語の置き換えはprh辞書で、辞書で書けない判定は`custom-rules/`で補う
- preset-jtf-styleの項目番号はJTFスタイルガイド第2.2版の番号であり、`rules/`の出典に使う第4.0版とは番号が違う。対応は[rules/notation.md](../rules/notation.md)の冒頭を参照

### 無効にしたルール

無効にしたルールと、対応するdocs-rulesのルール、無効にした理由は次のとおり。

| ルール | docs-rules | 無効にした理由 |
| --- | --- | --- |
| arabic-kanji-numbers | NOT-014 | 「一つ」を「1つ」に直すよう指摘する。NOT-014は和語の数え方を漢数字で書く |
| `1.1.1.本文` | GRM-001 | no-mix-dearu-desumasuと同じ箇所を重ねて指摘する。GRM-001の`判定`欄から外した |
| `1.2.2.ピリオド(.)とカンマ(,)` | NOT-002 | 全角の「．」「，」を半角の「.」「,」に直す候補を返す。NOT-002は「。」「、」に直す。また、このルールは一つのテキストの中で最初の一つしか指摘しないため、二つ目からを見落とす。docs-rules/not-002に置き換え、NOT-002の`判定`欄から外した |
| `2.2.2.算用数字と漢数字の使い分け` | NOT-014 | arabic-kanji-numbersと同じく、和語の数え方を算用数字に直すよう指摘する |
| `3.1.1.全角文字と半角文字の間` | NOT-022 | ja-space-between-half-and-full-widthと重複する |
| `3.2.カタカナ語間のスペースの有無` | NOT-017、NOT-023 | ja-nakaguro-or-halfwidth-space-between-katakanaと重複する |
| `4.2.1.感嘆符(！)`、`4.2.2.疑問符(？)` | NOT-003 | 全角で書くことを求めるが、NOT-003は「！」「？」を使わない。no-exclamation-question-markで判定する |
| `4.2.9.ダッシュ(-)` | なし | 第2.2版の項目で、第4.0版では削除されている（NOT-028の注記） |
| ja-space-after-exclamation、ja-space-after-question | NOT-003 | 「！」「？」を使わないため、判定する対象がない |

既定で無効の項目のうち、有効にしたのは`2.1.5.カタカナ`だけである。ほかの既定で無効の項目は次のとおりで、無効のままにする。

- preset-jtf-styleの辞書を使う項目：`2.1.2.漢字`、`2.1.6.カタカナの長音`、`2.2.1.ひらがなと漢字の使い分け`。漢字と仮名の判定は`data/`の内閣告示のデータとprh辞書で行う
- preset-ja-spacingのja-space-around-emphasisとja-space-around-strong

### #21で決めたこと

採点の入口を実装したとき（#21）に確かめ、決めたことは次のとおり。

| 項目 | 決めたこと |
| --- | --- |
| sentence-lengthの上限 | 既定値の100字にする。公用文作成の考え方の50〜60字は目安のため、60字を超える文はAI評価で扱う（GRM-002の注記） |
| no-mix-dearu-desumasu | 本文・見出し・箇条書の指定を空文字（自動判定）にする。空文字で動くことを確かめた |
| `1.1.1.本文`とno-mix-dearu-desumasu | 敬体と常体が混ざった文書で、同じ箇所を重ねて指摘した。`1.1.1.本文`を無効にし、GRM-001の`判定`欄から外した |
| `2.1.5.カタカナ`とno-hankaku-kana | 半角カナの例では`2.1.5.カタカナ`は何も指摘しなかった。重複がないため両方を有効のままにする |
| `3.1.2.全角文字どうし`とja-no-space-between-full-width | NOT-023の例（漢字と平仮名の間のスペース）を検出したのはja-no-space-between-full-widthだけだった。NOT-023の`判定`欄に足した |
| `3.3.かっこ類と隣接する文字の間のスペースの有無`とja-no-space-around-parentheses | NOT-024の例を検出したのはja-no-space-around-parenthesesだけだった。NOT-024の`判定`欄に足した |
| arabic-kanji-numbers | 「一つ」を「1つ」に直すよう指摘した。NOT-014（漢数字で書く）と食い違うため無効にする |
| `4.2.9.ダッシュ(-)` | 第4.0版で削除された項目のため無効にする |
| preset-jtf-styleの設定キー | パッケージの`rulesConfig`から確かめ、`textlintrc.json`に書いた |

## prh辞書

prh辞書のファイルと、扱うルール、作り方は次のとおり。

| ファイル | ルール | 作り方 |
| --- | --- | --- |
| [prh/manual.yml](prh/manual.yml) | FW-002、NOT-004、NOT-008、NOT-016、NOT-025 | 手で書く |
| [prh/okurigana.yml](prh/okurigana.yml) | NOT-010 | `data/okurigana.json`の許容の形から生成する |
| [prh/gairaigo.yml](prh/gairaigo.yml) | NOT-011 | `data/gairaigo.json`の用例集から生成する |

生成する辞書は、次のコマンドで作り直す。生成結果もリポジトリに置き、利用者の環境では生成しない。

```bash
python3 skills/docs-rules/evaluators/data/tools/build_prh.py
```

- NOT-010：告示の許容の形（「申込み」「行なう」など）を本則の形に直す。1字の形（「答」「問」）は熟語の一部に当たるため入れない。後ろに漢字が続く形（「申込書」）は、通則7の慣用の語として指摘しない
- NOT-011：用例集の語のうち語末が「ー」の語について、「ー」を省いた形を指摘する。両様の書き方が認められている語（「コンピューター／コンピュータ」）は指摘しない。語幹が3字未満の語（「スキー」「コピー」）は、ほかの語の一部に当たりやすいため入れない
- 生成した辞書のパターンが、判定データにある正しい語に当たる場合は辞書に入れない。スクリプトがその一覧を出す
- どちらも、判定できるのは判定データに例として挙がった語だけである

## 自前のルール

`custom-rules/`のファイルは、textlintの`--rulesdir`で読み込む。ルール名はファイル名に`docs-rules/`を付けたものになる。

| ルール | docs-rules | 判定すること |
| --- | --- | --- |
| [docs-rules/not-029](custom-rules/not-029.js) | NOT-029 | 年から書いた「2026/10/23」の形の日付。「2026年10月23日」に直す候補を返す。年のない「10/23」は分数と見分けられないため指摘しない |
| [docs-rules/not-033](custom-rules/not-033.js) | NOT-033 | 月か日を0で埋めていない「2026-4-1」の形の日付。「2026-04-01」に直す候補を返す。英字に続く形（「v2026-1-1」）は版の番号として扱い、指摘しない |
| [docs-rules/not-002](custom-rules/not-002.js) | NOT-002 | 全角の「．」「，」。「。」「、」に直す候補を返す。数字に挟まれたもの（「1．5」「1，000」）は小数点と桁区切りとみなし、半角の「.」「,」に直す候補を返す |
| [docs-rules/fw-008](custom-rules/fw-008.js) | FW-008 | 「〜せんとする」「〜べく」「〜べし」と、名詞を修飾しない「べき」。言い換えは文によるため、直し方の候補は返さない |
| [docs-rules/not-006](custom-rules/not-006.js) | NOT-006 | 常用漢字表の字種にない漢字。許容字体は表内として扱う。[allowed-terms.json](allowed-terms.json)の`NOT-006`に書いた専門用語（「脆弱性」）は指摘しない |
| [docs-rules/not-012](custom-rules/not-012.js) | NOT-012 | 4桁で「,」のない算用数字（1万以上はNOT-013で見る）と、「千」「百」を含む漢数字の数量（「千二百人」） |
| [docs-rules/not-013](custom-rules/not-013.js) | NOT-013 | 1万以上で「万」「億」「兆」を交ぜない数と、「千」「百」を単位にした数（「3千人」） |
| [docs-rules/mkd-010](custom-rules/mkd-010.js) | MKD-010 | リンクの文言の「こちら」「ここ」「リンク」など。prh辞書では本文のすべての語に当たるため、リンクの文言だけを見るルールにした |

- NOT-012とNOT-013は、番号とみなす次の数を対象にしない（[lib/numbers.js](lib/numbers.js)）
  - 英字や記号とつながった数（「ISO 8601」「v1.2.3」「2026-10-22」）
  - 「年」「号」「番」「版」「回」「目」「期」が後ろに続く数
  - 0で始まる2桁以上の数（電話番号の「09012345678」）
  - 「番号」「コード」「ID」「〒」の後ろの数（郵便番号の「1500001」）
- NOT-006の表外の音訓は実装していない。語の読みを決めるには形態素解析が要り、利用者に追加のインストールを求めることになるため。採点結果では`skipped_rules`に出し、AI評価で扱う。固有名詞もルールの対象外だが、文から見分けられないため指摘に含まれる

## markdownlint

Markdown記法のルール（[rules/markup.md](../rules/markup.md)）は、markdownlint-cli2で判定する。方針はtextlintと同じで、依存パッケージとして使い、判定条件を写して自前で書くことはしない。

### 実行方法

- 前提と入れ方：textlintと同じく、`score.mjs`が[package-lock.json](package-lock.json)の版で入れて実行する（上の「パッケージの入れ方」）
- 版：markdownlint-cli2の0.24.0に固定する。版を上げるときは、「設定の方針」の表とrules/markup.mdの`判定`欄を見直す
- Node.jsがない環境、パッケージを入れられない環境の扱いは、上の「終了コード」のとおり、そのことを伝えたうえでSKILL.mdの自己点検に戻る

開発者がリポジトリの直下で、リポジトリ全体のMarkdownにmarkdownlintだけを当てるコマンドは次のとおり。利用者の文書の採点には使わない。

```bash
npx -y markdownlint-cli2@0.24.0 --config skills/docs-rules/evaluators/docs-rules.markdownlint-cli2.jsonc "**/*.md"
```

指摘が0件なら何も表示されず、終了コードが0になる。`score.mjs`は同じ設定でmarkdownlint-cli2を呼び、`checker`を`markdownlint：MD0xx`として採点結果にまとめる。

### 設定の方針

既定で有効な全ルールを土台にし、docs-rulesの基準に合わせて設定を変える。無効にするのはMD013だけで、ほかは有効のままにする。`.github/`のテンプレートは対象外にする（#27でtextlintの対象からも外している）。

| ルール | docs-rules | 扱い |
| --- | --- | --- |
| MD001、MD003 | MKD-001 | MD003の`style`を`atx`にする |
| MD025、MD041 | MKD-002 | 有効 |
| MD018、MD019、MD022、MD023 | MKD-003 | 有効 |
| MD004 | MKD-004 | `style`を`dash`にする |
| MD029 | MKD-005 | `style`を`ordered`にする |
| MD005、MD007、MD030 | MKD-006 | 有効 |
| MD031、MD032、MD058 | MKD-007 | 有効 |
| MD040、MD046、MD048 | MKD-008 | MD046の`style`を`fenced`、MD048の`style`を`backtick`にする |
| MD036、MD049、MD050 | MKD-009 | MD049とMD050の`style`を`asterisk`にする |
| MD034、MD042、MD059 | MKD-010 | 有効。MD059の`prohibited_texts`に日本語の語を足すと、日本語の文言がすべて指摘される（0.24.0で確認）。このため既定の英語の語のままにする。「こちら」のような日本語の語はdocs-rules/mkd-010で判定する |

### 見出し階層と必須セクションの判定

- 見出し階層（1段ずつ下げる、見出し1は一つ、先頭は見出し1）は、標準のMD001・MD025・MD041で判定できる
- `schemas/`の必須セクション表との照合は、markdownlintの標準ルールではできない。MD043は見出しの一覧を設定ファイルに書く方式のため、`schemas/`を正本にできない。カスタムルールでも書けるが、#21で`score.mjs`が文書種別を受け取り、`schemas/<種別>.md`の表と文書の見出しを突き合わせると決めたため、markdownlint側では実装しない
