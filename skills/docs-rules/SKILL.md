# docs-rules

日本語の文書を、共通ルールと文書種別ごとの構成に沿って書くためのスキル。ルールの本体はこのファイルには書かず、下位ディレクトリに置く。このファイルには、どのファイルをどの順に読み、どう点検するかだけを書く。

## 1. 文書種別を決める

扱う文書種別は次の九つ。

| 種別 | 識別名 | 例 |
| --- | --- | --- |
| セッションログ | `session-log` | 作業セッションの経緯・決定事項・残課題のまとめ |
| 提案書 | `proposal` | 課題・提案内容・期待される効果を示す文書 |
| 学会論文 | `journal-paper` | 学会誌や論文誌に投稿する日本語の論文 |
| 学位論文 | `thesis` | 博士・修士・学士の学位を申請する日本語の論文 |
| UI文言 | `ui-text` | Webの画面のタイトル、ボタン、エラーなどの文言を、画面と要素ごとに並べた文言表 |
| ハウツー | `how-to` | 手順書、作業マニュアル、セットアップの手順、障害が起きたときの対処 |
| チュートリアル | `tutorial` | 入門、ハンズオン、初めて使う人向けの練習 |
| リファレンス | `reference` | 設定項目の一覧、コマンドの一覧、用語集、人が書く仕様の説明 |
| 解説 | `explanation` | 設計の背景、方針の説明、概念の説明 |

- 利用者が種別を言った場合：その種別を使う
- 利用者が種別を言わない場合：確認を挟まず、依頼内容から推定した種別で書く
- 「論文」とだけ言われた場合：学位の申請に使うと分かれば`thesis`、そうでなければ`journal-paper`にする
- 画面を実装しながら文言を書く場合：先に`ui-text`の文言表を書いて点検し、表の文言をコードに写す
- 手順や説明の文書の場合：読み手の問いで選ぶ。「どうすればよいか」は`how-to`、「教えてほしい」は`tutorial`、「何がどうなっているか」は`reference`、「なぜそうなのか」は`explanation`にする。問いが二つ以上ある依頼は、文書を分ける
- どの種別にも当てはまらない場合：種別を決めず、共通ルール（`rules/`）だけを適用する

## 2. 参照するファイルを読む

次の順に読む。後に読むものほど、その種別に固有の内容になる。

1. `rules/`：全種別に共通する表記・文体・Markdown記法のルール。先に`rules/README.md`を読んでルールの型と出典の略称を把握し、次に残りのファイルを読む
2. `schemas/<識別名>.md`：その種別の必須セクションと文書構造（例：`schemas/session-log.md`）
3. `templates/<識別名>.md`：その種別の見出しの型（例：`templates/proposal.md`）

- ファイルやディレクトリが存在しない場合は飛ばし、存在するものだけに従う
- 種別を決めなかった場合は、1だけを読む
- 共通ルールと種別ごとの定義が食い違う場合は、種別ごとの定義を優先する

## 3. 書く

- 2で読んだテンプレートの見出しの型に沿って書く。テンプレートがない場合は、スキーマの必須セクションを見出しにする
- テンプレートの案内のコメント（`<!-- -->`）は出力に残さない
- 必須セクションは省かない。書く内容がないセクションは、その旨を一文で書く

## 4. 点検してから出す

書き終えたら、出力する前に文書を採点・評価し、違反があれば書き直す。文書はファイルに保存して点検する。採点と評価の結果のJSON、書き直す前の版は、文書とは別の作業用の場所に保存する。

### 採点と評価

- 採点：`node <スキルのディレクトリ>/evaluators/score.mjs <文書のパス> --type <識別名>`を実行し、出力のJSONを保存する。`<スキルのディレクトリ>`は、このSKILL.mdがあるディレクトリの絶対パスである。Claude Codeでは、スキルを読み込んだときに「Base directory for this skill」として示される。作業フォルダはどこでもよい。種別を決めなかった場合は`--type`を付けない。終了コードが2なら引数を直す。`node`がない、または終了コードが3の場合は、採点を飛ばし、そのことを報告に書く。使い方の詳細は`evaluators/README.md`を参照
- 評価：`prompts/evaluate.md`の手順で、文書をAIで評価する。サブエージェントを使える環境では、評価をサブエージェントに渡す。`prompts/`がない場合は、2で読んだ`rules/`と`schemas/`に照らして違反を探す

### 書き直しの繰り返し

1. 採点と評価を1回ずつ行う。どちらにも違反がなければ、そのまま出力する
2. 違反を`prompts/rewrite.md`の手順で書き直す。1回目は採点と評価の両方の違反を渡し、2回目からは採点の違反だけを渡す。評価は実行ごとに結果が揺れるため、繰り返しには入れない
3. 書き直した版を採点し、`node <スキルのディレクトリ>/evaluators/compare.mjs <最初の採点結果> … <前回の採点結果> <今回の採点結果>`で、それまでの採点結果と比べる
4. `compare.mjs`の`new`に`SCHEMA`の違反があれば、書き直しで必須セクションの見出しを消したか動かしたことになる。案内のコメントを足したときも同じである。その回の書き直しを取り消して前の版に戻し、その回の採点結果を比べる列から外して、もう一度書き直す。取り消した回は回数に数えない。2回続けて取り消したときは、前の版で止める
5. `compare.mjs`の`stuck`の違反（2回続けて書き直した後も残った違反）と、`rewrite.md`が直せなかったと返した違反は、以降の書き直しに渡さない
6. 渡す違反がなくなるか、書き直しを3回行うまで、2〜5を繰り返す
7. 書き直しを1回以上行ったときは、最後の版を評価する。ここで出た違反は書き直さず、残った違反として報告する

採点を飛ばしたときは、書き直しを1回だけ行い、7に進む。

### 報告

点検の結果を、文書とは別の返答で利用者に示す。文書をファイルに保存する場合も、ファイルには報告を含めない。

```text
点検の結果：書き直し2回。直した違反7件（NOT-016、FW-001ほか）、残った違反1件
- 残った違反：GRM-005「今期の当チームの目標の中心は」（2回続けて残ったため対象から外した）
```

- 直した違反：`compare.mjs`の`fixed_total`と、1回目に渡した評価の違反のうち直せたものを合わせて数え、ルールIDを挙げる
- 残った違反：最後の採点と最後の評価の違反、直せなかった違反を、ルールID、`excerpt`、残った理由とともに挙げる。理由は「2回続けて残った」「書き直しの上限に達した」「最後の評価で見つかった」か、`rewrite.md`が返した理由とする
- 最初から違反がなかったときは、「点検の結果：違反なし」の1行にする
- 採点を飛ばしたときは、1行目にそのことを書き添える

### 改善点の候補

ルールや採点の不備を、スキルの改善点の候補として報告に足す。候補がなければ何も書かない。候補にする場面は次の四つ。

- 誤検出：採点か評価が、ルールや種別の例外に照らして違反でない箇所を指摘した
- 直せない違反：`compare.mjs`の`stuck`に残った違反と、`rewrite.md`が直せなかった違反
- 手で直した箇所：出力の後に利用者が直した箇所のうち、ルールが足りないために起きたもの
- 当てはまる種別なし：依頼がどの文書種別にも当てはまらなかった

```text
改善点の候補：NOT-003（誤検出）問いの形のボタンの「？」を指摘したが、種別の例外に当たる
```

報告に書いた後、`<スキルのディレクトリ>/../docs-rules-feedback/scripts/feedback.mjs`があれば、候補を1件ずつ保存する。

- コマンド：`node <そのパス> add '<JSON>'`。JSONに「'」が入るときは、引数ではなく標準入力で渡す
- JSONの項目：`type`（識別名）、`rule_id`、`scene`（場面の名前）、`reason`、`excerpt`（該当箇所。20字まで）
- ファイルがない場合（claude.aiなど）は保存しない。保存した候補は、`docs-rules-feedback`スキルでIssueにできる

参照先が一つも存在しない場合は、点検を省いてよい。
