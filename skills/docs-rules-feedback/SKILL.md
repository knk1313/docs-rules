# docs-rules-feedback

docs-rulesスキルを使ったセッションでためた改善点の候補を、Issueの下書きにして出すためのスキル。候補は、docs-rulesのSKILL.mdの「改善点の候補」の手順で、利用者の手元のファイルにたまる。このスキルは文書を書かない。

## 1. 候補を読む

`node <このスキルのディレクトリ>/scripts/feedback.mjs list`を実行し、ためた候補を読む。`<このスキルのディレクトリ>`は、このSKILL.mdがあるディレクトリの絶対パスである。

- 候補が0件なら、その旨を利用者に伝えて終える
- `node`がない場合は、候補を読めないことを伝えて終える
- 利用者がセッションの中で候補を直接示した場合は、その候補も加える

## 2. 出す先を決める

- 既定は`knk1313/docs-rules`にする
- 利用者が別のリポジトリ（自分の組織のフォークなど）を指定した場合は、そちらにする

## 3. 候補をまとめる

候補を`rule_id`と`scene`の組でまとめ、組ごとにIssueを1件にする。`rule_id`がない候補（当てはまる種別なしなど）は、`scene`ごとにまとめる。

- `gh issue list --repo <出す先> --state all --search "<rule_id>"`で、openとclosedの両方から同じ問題のIssueを探す
- 同じ問題のIssueがあれば、新しく立てず、そのIssueへのコメントの下書きにする

## 4. 下書きを作る

出す先の`.github/ISSUE_TEMPLATE/`のテンプレートの見出しのとおりに、全項目を埋める。テンプレートは場面で選ぶ。

| 場面 | テンプレート | タイトルのprefix |
| --- | --- | --- |
| 誤検出、直せない違反 | `バグ修正.md` | `fix:` |
| 手で直した箇所、当てはまる種別なし | `機能追加.md` | `feat:` |

- 「誰が書いたか」：AIエージェントが書いたことと、自分のモデル、ハーネスとその版を書く
- 「人が書く要約」：依頼した人の指示を、そのままの言葉で書く
- 「発生環境」：docs-rulesの版、インストール方法、ハーネス、モデル、OSを、分かる範囲で書く。分からない項目は「不明」と書く
- 候補の`recorded_at`、`type`、`reason`を、該当する見出しに書く
- `excerpt`（利用者の文書の抜粋）は、既定では載せない。載せると再現しやすいことを伝え、利用者が承認した候補だけ載せる

## 5. 承認を得てから出す

1. 下書きをすべて利用者に見せ、出してよいかを確かめる。承認されなかった下書きは出さない
2. 承認された下書きを、`gh issue create --repo <出す先> --title <タイトル> --body-file <下書きのファイル>`で出す。コメントの下書きは`gh issue comment`で出す
3. 出したIssueかコメントのURLを、利用者に伝える
4. 出した候補を`node <このスキルのディレクトリ>/scripts/feedback.mjs remove <id> ...`で消す。出さなかった候補は残す

`gh`がない場合や、`gh`の認証が済んでいない場合は、下書きのMarkdownを返して終える。候補は消さない。
